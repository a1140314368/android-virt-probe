# 测试环境边界

这一轮不改检测规则。Frida 17 对普通应用的漏报仍在，见上一次矩阵。这里只记调试器客户端、可写系统镜像和公开容器包实际走到哪一步。

## 原生调试器

已有事实：NDK `lldb-server gdbserver --attach` 会把目标进程停住，`/proc/<pid>/status` 的 `TracerPid` 变成非 0。进程停着时应用不能自己重扫。`killall lldb-server` 之后 `TracerPid` 回到 0。

宿主上的 NDK `lldb` 启动失败：

```
lldb: error while loading shared libraries: libpython3.11.so.1.0: cannot open shared object file
```

本机是 Ubuntu 24.04，Python 是 3.12.3。`apt-cache` 只有 `libpython3.12`，`apt-get install libpython3.11` 的结果是 `Unable to locate package libpython3.11`。

改用发行版客户端 `lldb-18`（1:18.1.3-1ubuntu1，对应本机 Python 3.12）：

1. `gdb-remote 5039` 能连上，进程停在 `SIGSTOP`，`TracerPid` 非 0。
2. 接着 `continue`，日志是 `Process 2931 resuming`，然后 `Process 2931 exited with status = -1 (0xffffffff) lost connection`。进程没能在仍被跟踪的状态下继续跑，所以应用没有写出新的扫描。
3. Ubuntu `gdb` 15.1 对同一 stub 报 `Target description specified unknown architecture "x86_64"`，随后 `The program is not being run`。
4. `lldb-server platform --listen '*:1234'` 后，`platform connect connect://127.0.0.1:1234` 报 `Failed to connect port`。

因此应用内的 attach-continue-scan-detach 还没闭环。缺的不是再写一条扫描规则，而是一个能在 `continue` 之后保持连接的调试客户端。最小条件：能加载的宿主 lldb，并且和这份 NDK `lldb-server` 在 `continue` 后不断连。当前发行版 `lldb-18` 会把进程打掉。

公开依据：LLVM 远程调试说明用 `lldb-server platform` 或 gdb-remote；AOSP《Use debuggers》写明 GDB 已不再提供，应用启动调试仍要先等调试器再 `continue`。X 上按 `lldb-server android gdb-remote continue` 检索没有可用帖子。

## 可写系统与 su

官方模拟器参数 `-writable-system` 的说明是：先带这个参数启动，再 `adb remount`，需要重启就重启后再 remount。API 35 `google_apis` x86_64 是 `userdebug`，`ro.debuggable=1`。

第一次 `adb remount` 只打印 overlayfs 并要求重启，`chmod` 仍是 `Read-only file system`。重启后第二次 `adb remount` 成功，`/system/xbin/su` 从 `rwsr-x---` 改成了 `rwxr-xr-x`。应用扫描仍然是「拒绝读取：/system/xbin/su」。这是 SELinux，不是 Unix 权限。随后已改回 `4750`，模式恢复为 `rwsr-x---`。

`/data/adb` 测试目录已删除，不把它算成 Magisk 正例。

## 容器

[BlackBoxing/BlackBox](https://github.com/BlackBoxing/BlackBox) 是 Apache-2.0。README 写支持 Android 5.0 到 12.0。2.2.0 发布了 `app-BlackBox64-release.apk` 和 `app-BlackBox32-release.apk`。

已用 `sdkmanager` 安装官方 `system-images;android-31;google_apis;x86_64`，镜像 `build.prop` 为 `userdebug`、`ro.debuggable=1`、API 31。AVD `virtprobe31` 能启动。

- 64 位包只含 `lib/arm64-v8a`。它在这台 x86_64 镜像上能装上并打开到 “Empty”，列表里只有它自己，没有 `io.virtprobe.sample`。
- 32 位包只含 `lib/armeabi-v7a`。安装失败：`INSTALL_FAILED_NO_MATCHING_ABIS: Failed to extract native libraries, res=-113`。

所以 API 35 没有包，并不等于所有 API 都不能测。API 31 x86_64 能启动，但这份公开 APK 没有 x86_64 原生库，克隆不了当前这个 x86_64 样本。要做真实容器正例，需要一份 x86_64 容器宿主，或一台能跑 arm64 的模拟器/设备，再装这份 arm64 BlackBox 和 arm64 样本。
